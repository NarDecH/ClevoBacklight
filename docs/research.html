3 จุดเปลี่ยน: ถอดรหัสจาก DSDT ของเครื่องเอง

ดึง ACPI tables จาก registry (HKLM\HARDWARE\ACPI) → แปลงด้วย iasl (ACPICA ใน tools/) → ค้น DSDT 4,000+ บรรทัด:

DSDT case 0x67 (~บรรทัด 24685)→ OperationRegion EC81 (~27721)→ mailbox EC RAM 0xF8–0xFC

คำสั่งที่ถอดได้ (WMBB(0, 0x67, ARGS) → Local7 = ARGS>>0x1C & 0xF)

ARGSสิ่งที่ EC ทำ
0x0สีเก่า 9-บิต: FDAT=(g|r<<3|b<<6)&0xFF, FBUF=bit8, FCMD=0xC2
0x1/0x2ไบต์เดี่ยว → reg 0x03/0x04 (breathe = 0x2A)
0x3cycle ทุกโซน: FDAT=0x06, FBUF=0x01, FBF1=0x03
0x7–0xBเอฟเฟกต์: random/dance/tempo/flash/wave = flags 0x07–0x0B
0xDความเร็ว: 0xFF - speed*0x19 ที่ reg 0x02
0xEไฟ: reg 0x0C = 0x3F เปิด / 0x20 ปิด
0xFสีรายโซน reg 0x03–05 payload B/R/G · brightness reg 0x06 = 63/126/189/252 (FCMD 0xCA)
ข้อค้นพบสำคัญ
FDAT 0x02–0x0C เป็น register IDs ของ mailbox ไม่ใช่ address EC RAM (0x02–0x0C จริงเก็บ fan/thermal)
พิสูจน์ mailbox มีชีวิต
FCMD เคลียร์กลับ 0x00 เองหลังทุกคำสั่ง = เฟิร์มแวร์ประมวลผลจริง + ยืนยันด้วยตา (แดง→เขียว→น้ำเงิน)

4 ชั้นเข้าถึง EC — ความปลอดภัยและความทนทาน

  • WinRing0x64.sys ลงนาม v1.2.0.5 — โหลด on-demand ผ่าน SCM (service WinRing0_1_2_0)
  • โปรโตคอล ITE ผ่านพอร์ต 0x66/0x62: read 0x80 / write 0x81 + เช็ก IBF/OBF
  • Hardening: cross-process mutex Global\ClevoBacklightEC · retry ×3 + backoff · drain OBF · single-instance daemon

5 เซ็นเซอร์อุณหภูมิ — ยืนยันข้ามแหล่ง

EC RAMความหมายการยืนยัน
0x07CPU temp (°C)45 == 45.1°C จาก MSAcpi_ThermalZoneTemperature เป๊ะ
0xC7GPU temp (°C)field VGAT ในบล็อก mirror ของ DSDT — แก้จากข้อสรุปเดิม 0x08 (ซึ่งคือ AC1 trip point ที่ ACPI เขียนลงไป ไม่ใช่ temp สด)

5.1 Fan registers (จากบล็อก mirror เดียวกัน — โหมด monitor ตั้งแต่ v1.9.1)

EC RAMFieldความหมาย
0x02FAN0(bit1) / FAN1(bit4)บิตสถานะนโยบายพัดลม (อ่านเชิงข้อมูล — ไม่ใช่สวิตช์ที่คุมพฤติกรรม EC ได้)
0xCE / 0xCFDUT1 / DUT2duty พัดลม CPU / GPU (0–255) — เซลล์ telemetry ที่ EC เขียนเอง
0xD0 / 0xD2RPM1 / RPM2 (16-bit)ความเร็วพัดลม (endianness auto-detect)

5.2 Fan tachometer mirror (ค้นพบ + แก้แล้ว, v1.9.10)

การดัมพ์ raw (ec_fan_dump.py / ec_fan_loadtest.py — อ่านอย่างเดียว) พบว่าบางช่วงเวลา EC สะท้อนค่าพัดลมเดียวไปทั้งสองช่อง — RPM1[0xD0] = RPM2[0xD2] และ DUT1[0xCE] = DUT2[0xCF] เท่ากันเป๊ะทุก sample (เช่น 05 05 = 1285 @ duty 5% idle) ส่วนค่า 3 ↔ 771 ที่เคยอ่านได้คือ transient ของ tachometer ไม่ใช่พัดลมหยุดหมุน

→ read_fan_once ตรวจ mirror (RPM + raw duty เท่ากันเป๊ะและไม่ใช่ศูนย์) แล้วรายงาน GPU fan = 0 — Dashboard ไม่แสดงพัดลมหลอก · unit test mirror-collapse ครอบ · ยืนยันบนเครื่องจริง: cpu_rpm ≈ 1450, gpu_rpm = 0

Fan control: proven absent (ทดลองบนเครื่องจริง, v1.9.1) — หลักฐาน 3 ชั้น:
  1. เขียน DUT1=65% ครั้งเดียว → EC ดึงกลับเป็น ~30% ภายใน ~1 วินาที
  2. ยิงซ้ำ 4 Hz (แบบ NBFC) → duty ค้าง 65% ใน RAM แต่ RPM นิ่ง 1452 ตลอด = EC ไม่เอาค่าไปขับ PWM
  3. grep ทุก case ในตัวจัดการ mailbox ของ DSDT → ไม่มี write path ถึง DUT/RPM เลย (มีแค่ 0x67=คีย์บอร์ด, 0x27)
สรุป: clevo_fan.py เป็น monitor อ่านอย่างเดียว (status / watch + unit test การันตีไม่มีการเขียน EC) — โค้ด controller ถูกลบ กู้ได้จาก git history ถ้าพอร์ตไปรุ่นที่คุมได้

กลายเป็นโหมด temp-reactive (ไล่สี cyan→เขียว→เหลือง→แดง + กระพริบเตือน ≥90°C) และ health check ของ daemon · เครื่องรุ่นอื่นใช้ --dump-ec --diff สำรวจ address เองได้ (hardware profile)

9 ช่องทางที่ยังเปิดสำหรับงานต่อ
